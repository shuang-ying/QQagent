# 合并转发消息阅读

## 使用

在私聊发送合并转发，或群里 @机器人并附带合并转发，再提出问题。也可以先发送转发、随后 @机器人问“总结刚才的转发”，或者引用本话题内旧的合并转发提问。允许的群消息仍会入库，不被 @ 时保持原有主动/被动策略。

机器人通过标准 OneBot v11 `get_forward_msg` 获取正文，兼容 `message` 中的 `node` 数组及常见 `messages` 返回格式。支持事件中直接包含的节点、CQ 转发段，以及 `com.tencent.multimsg` JSON 卡片中的资源 ID；不会对无关卡片乱调用接口。[OneBot API 规范](https://github.com/botuniverse/onebot-11/blob/master/api/public.md#get_forward_msg-获取合并转发消息)

## 实现

- 将原作者姓名、QQ、原时间、节点序号和正文标为引用资料；实际发送者与回复对象始终采用外层事件身份。转发作者不会被注册为本群的新发言者。
- 转发图片沿用原有图片解码、视觉模型和预算逻辑，来源说明同时标注转发者与节点原作者。未读取图片会按现有图片处理流程降级。
- 白名单/黑名单和群准入在读取之前检查。转发里的 @ 不触发被动回复，`/forget` 等内容只作为资料，不执行命令。
- 事实抽取只接收外层文字，排除转发正文；不会把原作者的“我喜欢……”写成转发者的喜好。外层发送者附带的本人自述仍可记忆。情绪分析不使用合并转发正文。
- 入站先落库，回复实际开始时冻结窗口，再展开本窗口内的转发；读取期间新到消息不扩大已冻结窗口。切换话题会取消旧轮次。
- 解析结果写回原消息行，供后续问答、主动回复及历史上下文使用；复用原表结构，不新增依赖或数据库迁移。

## 资源限制与失败处理

单次展开最多50个节点、3层嵌套、16张转发图片、16000个正文字符、8次资源请求，时间上限5秒；本轮窗口按最近20条记录进行检查，总读取预算8秒。循环嵌套跳过，同次展开的相同资源ID只请求一次。单节点最多256个消息段。本轮转发正文会按实际模型上下文预算截取，明确说明未纳入的内容，已读取的记录仍保留；图片沿用原有预算裁剪。

接口不支持、资源过期、无ID、异常格式或超限时，明确保留“未读取/截断”的说明，正常聊天继续，不编造正文。只有普通消息ID而没有正文的 `node` 不会被误当成转发资源ID。

## 验证

执行 `npm run test:forward-messages` 可运行27项本地模拟检查，无需真实QQ或模型服务。重启Agent后生效，现有配置兼容。
